# STL-SVPIO — Reproduction Notes

This repository documents an attempt to reproduce the point-mass results of the
`stl-svpio` paper from the public repository (`hzheng40/stl-svpio`). Claims are
split explicitly into **findings supported directly by data** and **hypotheses**.
Hypotheses are labelled as such and are not asserted as fact.

> Scope: this document currently covers **Table I** only (plus the reach-avoid
> feasibility strips below). Figure 3 and the detailed feasibility/tuning analysis
> will be added after the sweep and the full 100-seed run.

---

## Environment / getting it to run

Required before any result could be produced (independent of the reproduction
question):

- `nvidia-smi` initially failed with an NVML driver/library version mismatch;
  resolved by a reboot to reload matching kernel modules.
- Cold CUDA init intermittently failed (`cuInit` → `CUDA_ERROR_NO_DEVICE` / `999`);
  resolved by enabling the persistence daemon (`nvidia-persistenced`), which
  survives reboots (unlike `nvidia-smi -pm 1`).

## Table I — single-agent reach-avoid

**Finding (supported by data): the committed pipeline does not reproduce its own
reference CSV.**

A pristine checkout was installed in an isolated environment with the locked
`stljax==1.1.3` and run on CPU. Result versus the committed reference
(`results/reference/table1_reach_avoid_summary.csv`), robustness values:

| method | reference | this repo, clean run | local machine (GPU) |
|---|---|---|---|
| stl_svpio | **+0.108** | −2.471 | −0.399 |
| mppi | +0.005 | **−0.797210** | **−0.797210** |
| dpi | **+0.179** | crashes (see below) | −3.500 |

Two points make this a firm conclusion rather than an environment artifact:

1. **MPPI is bit-identical** between the clean install (−0.797210) and the local
   GPU run (−0.797210). The pipeline is deterministic for MPPI, and the local
   environment faithfully reproduces the committed code. What fails to match is
   the reference, not the machine.
2. **DPI, SVMPC, and STLCG-GD cannot run as committed.** Their configs set
   `stl_temperature: null` while inheriting `stl_approx_method: logsumexp`, and
   `stljax` raises `AssertionError: need a temperature value` for that
   combination. A clean checkout crashes on these methods.

**Components that were checked and are correct in isolation** (so the defect is
*not* here):

- The STL specification under `stljax==1.1.3`: a hand-constructed trajectory that
  reaches the goal scores robustness **+0.5**; a trajectory that stays at the
  start scores **−3.5** (which equals the goal predicate evaluated at the start
  state, `0.5 − |0 − 4| = −3.5`). The objective is correct.
- The dynamics: a standard double integrator
  (`pos += dt·vel + ½·dt²·a`, `vel += dt·a`), control bounded at ±5, which over
  20 steps of `dt=0.1` can reach the goal comfortably.
- Controller sign conventions: cost is `−robustness`; importance weights favour
  low cost; `best` selection returns `argmin(cost)` = max robustness. Consistent.
- Step-size anneal wiring: the YAML keys `svgd_step_anneal` / `svgd_step_final`
  are correctly mapped to the controller fields. Not a dropped-config bug.

**Hypothesis (not proven here):** the committed reference CSVs were generated by
the authors' original development code, not by the repackaged entry points in
this repository. This is consistent with (a) the repository's own statement that
it is organised "for reproducing the paper results rather than preserving every
exploratory script from the development repository", and (b) the fact that the
committed code demonstrably does not regenerate the committed numbers. It is the
most economical explanation but is not directly proven by the data here.

## What is and is not claimed (Table I)

**Supported directly by data:**
- The committed repo does not regenerate its Table I reference (clean-install run;
  MPPI bit-identical to local; DPI/SVMPC/STLCG-GD crash on `stl_temperature: null`).
- The STL objective, the dynamics, the controller sign conventions, and the anneal
  wiring are individually correct.

**Hypothesis (labelled, not asserted as fact):**
- The reference numbers were produced by original/dev code rather than these
  repackaged entry points.

**Explicitly not claimed:** that the method or the paper's conclusions are wrong.
The failure here is to reproduce the specific Table I numbers from this repository.
